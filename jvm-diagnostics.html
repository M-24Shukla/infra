01 / JVM diagnostics

Choose the evidence before the tool

Heap, threads, native memory and JMX answer different questions. Examples target HotSpot/JDK 21; check the actual target JVM help.

A quick diagnostic decision map

SymptomFirst evidenceNext investigation
Heap grows between comparable GC cyclesHeap/live-set trend, workload, queue/cache sizesHistogram trend, heap ownership and retention path
Container memory grows but heap is stableContainer/RSS trend, thread/direct-buffer metricsNMT if already enabled, OS mappings, native allocations
High CPUProcess/thread CPU samples and request rateJFR profile; repeated stacks for the hot work
High latency with low CPUTraces, pool waits, queue delayRepeated thread dumps and downstream timing
Suspected deadlockThread dump with lock informationConfirm ownership/wait cycle and code locking order
Need an interactive overviewExisting metrics or JMX monitoringJConsole for JVM charts and MBeans

A heap dump is a snapshot of objects/references. A thread dump is a snapshot of execution stacks/locks. A JFR recording captures a time window of enabled events. None alone proves the full incident mechanism.

Interview questions · try answering first
Which dump should I take for slow requests?
Start with request timing and thread/pool evidence. Take repeated thread dumps for blocked work; use JFR for CPU/locking/allocation timing. A large heap dump is not automatically the right first step.
Can one tool diagnose every kind of memory issue?
No. A Java heap view does not account for every native allocation or container memory category. Match evidence to the suspected layer.
02 / JVM diagnostics

Heap and memory foundations

Understand what is being measured before calling growth a leak.

Heap, stacks, metaspace, direct memory and RSS

TermMeaning / common trap
HeapObjects managed by GC. Used, committed and maximum heap are different values.
Thread stacksPlatform threads consume native stack resources; thread growth can exhaust native memory.
MetaspaceClass metadata; growth can relate to class loading and class-loader retention.
Direct/native memoryBuffers, JVM/native libraries and other allocations outside ordinary object storage.
RSS / container memoryOS/container views of resident/accounted memory; not equal to Java heap used.
Allocation / retentionCreating objects versus keeping them reachable beyond their useful lifetime.

A warm cache or startup class loading may grow and then stabilise legitimately. An unbounded cache or accumulated queue can retain memory indefinitely. The diagnosis depends on the expected ownership and workload, not simply the object count.

Read in context: JVM memory charts ↗Shallow and retained memory ↗
Interview questions · try answering first
Can GC collect a logically unused object?
Only if it is no longer strongly reachable under GC reachability rules. If an application collection still holds it, GC cannot know that the business no longer needs it.
Does memory staying high after GC prove a leak?
No. Check the measurement: committed heap or RSS may stay high although live objects shrink. Also compare legitimate cache/workload growth and the collector behavior.
How can a tiny object retain hundreds of megabytes?
It may reference a large graph of other objects. Its own shallow size can be small while the graph kept alive by it is large.
03 / JVM diagnostics

JConsole: live JVM monitoring through JMX

JConsole is a graphical JMX client shipped with the JDK. It provides interactive monitoring; it is not a CPU profiler or automatic RCA engine.

Connect and read the tabs

For a local learning process, run JConsole as the same OS user and select the correct JVM. For a remote service, connect to an existing approved JMX endpoint. Confirm service identity, JVM uptime and version before interpreting a chart.

TabWhat to look at
OverviewCPU, memory, thread and class trends together.
MemoryUsed/committed/max by pool; compare behavior across GC cycles.
ThreadsThread-count trends, individual stacks and the deadlock detection action.
Classes / VM SummaryClass-loading trend, uptime, VM identity and configuration context.
MBeansManaged attributes and operations, including application-specific instrumentation.

Chart observations generate hypotheses: rising threads suggest creation/cleanup issues; heap growth may suggest retained work. Verify those possibilities with ownership or execution evidence.

Diagnostic commands
# On your workstation / local development environment:
jconsole
# Attach to a selected local JVM; do not assume the PID:
jconsole <pid>
# Existing authorised remote endpoint:
jconsole <jmx-host>:<registry-port>
Read in context: Using JConsole ↗
Interview questions · try answering first
What is JMX?
Java Management Extensions provides management interfaces exposed through MBeans. JConsole is one client of those interfaces; the management interface and its visual client are separate.
Should I click Perform GC when memory rises?
Not as a routine fix. It requests GC and changes the system being observed; it may be expensive and may be disabled/handled differently by the JVM. First use natural GC trends and workload context.
Can JConsole tell me the exact source line causing a leak?
Not from a memory chart alone. It helps narrow the symptom; heap ownership, reference paths, source inspection and sometimes allocation profiling establish the cause.

Remote JMX in Kubernetes: registry, RMI and security

JMX commonly uses an RMI registry endpoint plus a returned connector endpoint. Forwarding just the registry can fail if the connector advertises an unreachable host/port. A port-forward is transport, not automatic JMX configuration or authentication.

Use the organisation’s authenticated and encrypted JMX setup. Do not expose an unauthenticated management port or turn off TLS just to connect. Some MBean operations can change runtime behavior or write dumps. The example below assumes both endpoints are already configured for forwarding on known ports, with reachable advertised address and valid TLS configuration.

Existing endpoint / transport example
# Inspect existing setup before starting a forwarding session:
kubectl get pod <pod> -n <ns> -o yaml
# Workstation: local transport to an already configured JMX service
kubectl port-forward -n <ns> pod/<pod> 19099:9099 19100:9100
# Client credentials/trust must use the approved JMX configuration.
# A connection to localhost:19099 alone will not fix an incorrect
# RMI advertised address or certificate hostname mismatch.
Read in context: Remote JMX configuration and security ↗
Interview questions · try answering first
My JMX registry connects, but JConsole still fails. Why?
Inspect the connector endpoint advertised by RMI, its reachability, both ports, credentials and TLS trust/hostname. Check whether the target uses one or two configured ports. A successful registry TCP connection is only the first step.
Does kubectl port-forward make any JMX configuration safe?
No. API permissions control who can forward; JMX authentication/authorisation, encryption, binding and credential handling still need deliberate configuration.
04 / JVM diagnostics

Capture evidence with jcmd

Prefer a specific PID and a compatible JDK tool. These are examples to study, not commands run against your environment.

Find the target and check command impact

Run attach tools in the correct PID/user/container context. An image may contain a JRE without jcmd, or attach may be disabled. Do not assume the JVM is PID 1. Check help on the actual target before capture. File arguments are written by the target JVM in its filesystem; shell redirection is performed by the shell running the client command.

Diagnostic commands
# Discover processes visible in this context; argv can contain secrets:
jcmd -l
# Specific target only:
jcmd <pid> VM.version
jcmd <pid> VM.flags
jcmd <pid> help
jcmd <pid> help GC.heap_dump
jcmd <pid> help GC.class_histogram
jcmd <pid> help Thread.print
jcmd <pid> GC.heap_info
Read in context: jcmd commands and impact ↗
Interview questions · try answering first
Why not run jcmd 0?
PID 0 can target all discoverable JVMs. Choose the exact service PID to avoid unrelated processes and unexpected diagnostic cost.
Is jcmd read-only and cost-free?
No. Commands vary: some inspect metadata, others walk the heap, request GC, write recordings or alter VM settings. Read impact/help and plan capacity.
05 / JVM diagnostics

Heap dumps and histograms

Use heap evidence to find what remains reachable and who owns it. Capture may pause the JVM and produce large sensitive files.

Capture a histogram, heap dump or OOM dump

A histogram groups objects by class; it shows counts/bytes without the full reference graph. A heap dump supports deeper object/reference analysis. Both can be high-impact; avoid uncontrolled repeated capture. Default live-object collection can request full GC; options differ by target version. Dumps can contain tokens and request data, so restrict access and storage.

Potentially high-impact capture / startup options
# Potentially high-impact heap inspection:
jcmd <pid> GC.class_histogram > histogram-01.txt
# HPROF file path is inside the target JVM filesystem:
jcmd <pid> GC.heap_dump /diagnostics/heap-01.hprof
# Legacy alternative: select one capture method, not all at once:
jmap -dump:live,format=b,file=/diagnostics/heap-02.hprof <pid>

# Startup options, configured before a future failure:
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/diagnostics
# Ensure this directory exists, is writable and has sufficient space.
Read in context: Heap command options ↗OOM dump startup options ↗Legacy jmap syntax ↗
Interview questions · try answering first
Will HeapDumpOnOutOfMemoryError capture every Kubernetes OOMKilled?
No. A cgroup/kernel kill can terminate the process without a Java OutOfMemoryError or time to write a dump. JVM OOME and container OOM termination are different mechanisms.
Can I capture a heap dump on readOnlyRootFilesystem?
Yes, if an appropriate writable mounted destination exists and the JVM user can access it. Plan free space and storage lifetime; do not assume /tmp is large or persistent.
Is the largest histogram class necessarily the leak owner?
No. byte[] or String may be payload retained by another object. Follow ownership and paths rather than blaming a common payload class.

Read a heap dump in Eclipse MAT

Open the HPROF in Eclipse Memory Analyzer (MAT). Start with Leak Suspects as a lead, then inspect Histogram and Dominator Tree. A dominator is on every reference path from roots to a dominated object. Use retained size to find substantial ownership graphs; use Paths to GC Roots to understand why a suspect stays alive. Interpret weak/soft references carefully.

Example: many request payloads are dominated by a long-lived application map. A path through a static holder → map → entries → payloads explains retention. Now inspect the insertion/removal policy in code. Do not simply delete all large maps: a bounded useful cache may be correct.

Read in context: Finding a leak ↗Retained heap definition ↗Leak Suspects report ↗
Interview questions · try answering first
What is shallow size versus retained size?
Shallow size is the object’s own storage. Retained size represents memory that becomes collectible if that object becomes unreachable, accounting for the objects retained through it. Shared references make simple summed guesses unreliable.
Does the Leak Suspects report prove a bug?
No. It identifies substantial retention patterns. Validate against expected lifetime, workload, source code and a comparable later snapshot.
What is the difference between allocation site and retention path?
Allocation site says where an object was created. Retention path says what keeps it alive. The creating method may be correct while a different owner forgets cleanup.
06 / JVM diagnostics

Find and prove a memory leak

A useful investigation needs a growth trend, an incorrect owner/lifetime and a verification plan—not just one large snapshot.

A repeatable investigation workflow

  • Define expected lifetime. Does an entry belong to one request, one user session, a bounded cache or the entire service lifetime?
  • Establish a comparable workload. Track traffic, data volume, queue/cache size and memory over time. Separate warm-up from steady state.
  • Classify the growth. Is it heap live objects, loaded classes, threads, direct/native memory or filesystem/cache accounting?
  • Identify the retained owner. Compare suitable snapshots/histograms, inspect retained graphs and follow root paths.
  • Validate the source path. Read the actual deployed code/configuration that adds and removes the retained data.
  • Prove the fix. Repeat the same workload, drain or expire work as specified, and verify bounded retention and correct behavior.

Watch the post-collection live set across comparable cycles and workload; a rising baseline is a clue. A continuously rising RSS graph alone cannot distinguish retained heap from other memory. Do not force full GC repeatedly just to draw a cleaner graph.

Read in context: Memory-leak investigation ↗
Interview questions · try answering first
How do you distinguish a leak from a cache?
Check the cache contract: capacity/expiry, reachable owner and workload. A cache that reaches a designed bound can be healthy; an unintended unbounded cache can be the leak. Names do not determine correctness.
What would you measure after the fix?
Comparable traffic and data, live-set/retained-object trend, cache/queue bounds, GC time, latency, throughput and errors. A longer soak test checks accumulation that a brief unit test can miss.

Common Java retention bugs and the right fix

PatternWhy memory remains / what to inspect
Static map or unbounded cacheLong-lived owner holds every inserted object. Define capacity/expiry and correct removal.
ThreadLocal on pooled threadsValues can survive across tasks; use lifecycle cleanup, typically remove() in finally when appropriate.
Listener / subscription registryUnregistered callbacks retain subscribers and their object graphs.
Unbounded queue / executor backlogWork arrives faster than processing; bound work and apply overload policy.
Future / request tracking mapCompleted, timed-out or cancelled work may not leave the map. Exercise every terminal path.
Class-loader retentionOld loaders remain reachable through threads, caches or references; inspect repeated loading/redeployment.

Your Kafka work makes queue retention particularly relevant: if a slow downstream causes payloads to accumulate in application memory, increasing heap postpones the failure. Apply bounded admission and correct completion/offset semantics; do not silently drop reliable messages.

Read in context: ThreadLocal lifecycle ↗Executor queues and overload ↗
Interview questions · try answering first
Why can ThreadLocal be a problem with a thread pool?
The thread is reused and can outlive the request. If cleanup is missing, the value can remain associated with it and may also leak request context into another task.
Are virtual threads a cure for memory leaks?
No. They change concurrency cost, but objects, tasks and downstream resources still need bounded lifetime/capacity. More in-flight work can increase memory pressure.
Would System.gc() fix an unbounded map?
No. Strongly reachable entries remain live. Fix ownership, expiry or removal; requesting GC cannot infer business intent.
07 / JVM diagnostics

Thread dumps: read stacks, locks and progress

Take a small series of snapshots across the incident window. One frame can be a normal transient state.

Capture and compare execution snapshots

A thread dump lists thread stacks and, with supported options, lock information. Compare a few snapshots several seconds apart: persistent waiting or repeated hot frames are more useful than one observation. Use a bounded capture plan rather than an uncontrolled loop. A typical application may have many legitimately idle waiting threads.

Diagnostic commands
# Three separate samples during the same symptom window:
jcmd <pid> Thread.print -l > threads-01.txt
# Wait roughly 5–10 seconds before the next sample:
jcmd <pid> Thread.print -l > threads-02.txt
# Wait again, then:
jcmd <pid> Thread.print -l > threads-03.txt
# Legacy alternative; not an additional mandatory capture:
jstack -l <pid> > threads-legacy.txt
# On typical HotSpot Unix platforms, SIGQUIT can print to JVM output:
# kill -QUIT <pid>
# Confirm signal handling/log routing first; do not confuse with SIGKILL.
Read in context: Thread stacks and locks ↗Thread.print help ↗
Interview questions · try answering first
Why collect multiple thread dumps?
A single stack captures one instant. Repeated stacks help distinguish normal waiting from persistent blockage or lack of progress, although CPU evidence is still needed for a hot-thread claim.
Can a dump identify a Java deadlock?
Many conventional monitor/ownable-synchronizer deadlocks can be reported. Not every application-level dependency cycle is detected, such as tasks waiting for other tasks starved in the same executor.

Thread states and a concrete lock example

State / observationInterpretation
RUNNABLEEligible/running or in some native operations; does not prove continuous CPU consumption.
BLOCKEDWaiting to acquire a Java monitor, often synchronized.
WAITINGIndefinite wait such as park/join/wait; inspect the primitive and caller.
TIMED_WAITINGBounded wait such as sleep, timed park or timed wait.
Many pool workers parkedMay be idle and healthy; correlate queue depth and incoming requests.
Repeated pool-acquire framesCould indicate resource starvation; inspect pool usage and owners.

Illustration: two request threads repeatedly wait for the same monitor while its owner is in a slow operation. Follow the owner’s stack and code; a smaller lock scope might be needed, but verify consistency before moving work outside a lock.

Illustrative output
# Illustrative excerpts, not output from your service:
"request-17" ...
  java.lang.Thread.State: BLOCKED (on object monitor)
  at example.OrderService.update(OrderService.java:72)
  - waiting to lock <0x000000001234> (a example.OrderService)

"worker-4" ...
  at example.RemoteClient.call(RemoteClient.java:40)
  at example.OrderService.update(OrderService.java:79)

Interview questions · try answering first
If I see WAITING, should I replace synchronized?
No. Identify the actual primitive and reason. BLOCKED commonly relates to intrinsic monitor entry; locks/conditions and queues often park threads in WAITING/TIMED_WAITING. Idle waiting is normal.
How do you prove a CPU hotspot?
Correlate per-thread CPU deltas or a profiler with stack samples. On Linux, platform-thread native IDs may be matched to dump nid values, but namespace IDs must align. A RUNNABLE label alone is insufficient.

Java 21 virtual-thread caveats

Traditional thread views are not a complete inventory of virtual-thread work. Where supported, use the new thread dump command and inspect target help. Do not equate a virtual thread with a permanent OS thread ID. JDK 21 pinning behavior and event details can differ from later JDK releases; explain which version you mean.

Diagnostic commands
jcmd <pid> help Thread.dump_to_file
# File is written in the target JVM filesystem:
jcmd <pid> Thread.dump_to_file -format=json /diagnostics/threads.json
Read in context: Virtual-thread debugging ↗
Interview questions · try answering first
Why does JConsole show fewer threads than my virtual-thread tasks?
Traditional management views do not represent virtual threads in the same way as platform threads. Use version-appropriate virtual-thread diagnostics and application-level in-flight metrics.
Does a virtual-thread dump provide exactly the same lock information?
No. The newer dump format has different contents and purpose from traditional full thread dumps. Check the version documentation and use complementary evidence.
08 / JVM diagnostics

Native memory and JFR

Use complementary evidence when heap objects do not explain process growth or when the problem needs timing.

Native Memory Tracking: baseline and diff

Enable NMT at JVM startup if the diagnostic plan needs it. It cannot be newly enabled with jcmd after starting without it. Compare baseline/diff categories to identify growing JVM-managed native areas. Reserved address space is not the same as committed or resident memory.

NMT has overhead and does not track every allocation made by third-party native code. A reassuring NMT summary does not rule out all native leakage. Compare OS mappings, thread counts and relevant native/library metrics as needed.

Startup setting + diagnostic comparisons
# Startup option; requires a planned JVM launch/restart:
-XX:NativeMemoryTracking=summary
# Once enabled, on the target JVM:
jcmd <pid> VM.native_memory summary scale=MB
jcmd <pid> VM.native_memory baseline
# After a comparable workload interval:
jcmd <pid> VM.native_memory summary.diff scale=MB
# Linux process view (permissions/tools permitting):
pmap -x <pid>
cat /proc/<pid>/status
Read in context: NMT scope and limitations ↗
Interview questions · try answering first
Heap is stable but RSS rises. Is it definitely a native leak?
No. Investigate native allocations, thread growth, mappings, allocator behavior and relevant accounting. Establish persistent unwanted growth and an ownership/cause before calling it a leak.
Can I add NMT flags to a running Pod without restarting?
Changing the Deployment spec affects replacement containers, not the already running JVM. Plan startup enablement if NMT is needed; use available evidence for the current process.

JFR and JMC: capture a time window

JFR records enabled runtime events; JMC provides a graphical analysis environment. Use a bounded recording for execution samples, GC, allocations, locks and other configured events. Sampling and event thresholds mean absence of an event is not proof nothing happened. JFR is not a complete heap-reference graph.

Bounded recording / offline inspection
# Writes a recording inside the target filesystem:
jcmd <pid> JFR.start name=incident settings=profile duration=60s filename=/diagnostics/incident.jfr
jcmd <pid> JFR.check
# On a workstation after secure retrieval:
jfr summary incident.jfr
jfr print --events jdk.GarbageCollection incident.jfr
# Open the file in JDK Mission Control for timeline/profile analysis.
Read in context: JFR command and events ↗JDK Mission Control ↗
Interview questions · try answering first
When do I choose JFR instead of a heap dump?
Use JFR for time-correlated behavior such as CPU, allocation and locks. Use a heap dump for detailed object ownership. The tools complement each other; neither is an automatic substitute.
Will default allocation samples show every allocation?
No. Understand which events/settings are enabled and how they sample. Use them to locate likely allocation pressure, then verify the retention or execution mechanism separately.
09 / JVM diagnostics

Collect diagnostics in Kubernetes

Permissions, file paths and lifecycle determine whether your planned diagnostic actually succeeds.

PID, user, tools and capture destination

Inspect target identity, restarts, last termination and mounted paths. The following assumes jcmd exists in the application container. A debug image or ephemeral container does not automatically grant compatible tooling, PID visibility, user/attach permissions or access to the target filesystem.

Select a writable destination with adequate capacity. Disk-backed emptyDir survives container restarts within the same Pod, but not Pod deletion; a suitable persistent volume can preserve files longer. A memory-backed emptyDir consumes memory and is a poor default destination for a large heap dump.

Capture / transfer examples with diagnostic cost
kubectl describe pod <pod> -n <ns>
kubectl logs <pod> -n <ns> -c <container> --previous
kubectl exec <pod> -n <ns> -c <container> -- jcmd -l
kubectl exec <pod> -n <ns> -c <container> -- jcmd <pid> help GC.heap_dump
# Local redirection saves the textual thread dump on your workstation:
kubectl exec <pod> -n <ns> -c <container> -- jcmd <pid> Thread.print -l > threads-01.txt
# The JVM writes this heap dump inside the container mount:
kubectl exec <pod> -n <ns> -c <container> -- jcmd <pid> GC.heap_dump /diagnostics/heap-01.hprof
# Transfer sensitive diagnostic file to an approved workstation location:
kubectl cp -n <ns> -c <container> <pod>:/diagnostics/heap-01.hprof ./heap-01.hprof
# kubectl cp normally needs tar in the container; verify support first.
Read in context: Pod diagnostics ↗Ephemeral volume lifetime ↗kubectl cp requirements ↗
Interview questions · try answering first
Why does kubectl exec permission not guarantee JVM attach works?
OS identity, PID/mount namespace, target attach settings, filesystem permissions and tool compatibility still apply. API authorisation is a separate layer.
Will restarting the Pod help preserve a heap dump?
Not necessarily. It may erase the relevant process state and Pod-local storage. Collect and securely preserve available evidence before replacement when incident priorities permit.
How do security contexts affect capture?
Non-root identity and read-only root filesystem require appropriate attach permissions and writable mounted paths. Do not solve capture failures by broadly granting privileged mode.
10 / JVM diagnostics

Interview scenarios and your experience

Practise the next check and the expected result before revealing the answer.

Scenario questions

Use your production RCA, Kafka throughput work and shell diagnostic suite as real context. These are prompts to connect experience, not claims that you already implemented JConsole/MAT/NMT integrations.

Interview questions · try answering first
After deployment, heap baseline grows at stable traffic. What would you do?
Confirm comparable load and metric/GC meaning, inspect cache/queue/class trends, then use suitable heap evidence to find the retaining owner. Compare the owner lifecycle with the deployed changes and repeat a controlled test after the fix.
Requests hang but CPU is low. How do thread dumps help?
Compare a small series for persistent waits, shared locks and pool-acquire frames. Identify the owning threads or exhausted dependency; correlate request traces and pool metrics. Low CPU can reflect waiting rather than health.
A consumer queue grows until OOM. Is the collection the root cause?
The queue is the retention point, but investigate why arrival exceeds processing and why the queue is unbounded. Fix capacity/admission and downstream progress with correct delivery semantics.
My service is OOMKilled, but no heap dump exists. Why?
Check whether the kernel killed it rather than the JVM throwing OOME. Also inspect configured path, permissions, free capacity and file lifetime. No dump does not establish no memory issue.
How could your diagnostic suite include JVM evidence?
Add an opt-in capture plan: identity, VM flags, heap summary and bounded thread snapshots first; make high-impact heap capture separately deliberate. Record timestamps, target container/PID, failures and artifact paths, with redaction and timeouts.
AI says a static map is leaking. How do you validate that?
Confirm that deployed code uses the map on the affected path. Show that it retains objects beyond intended lifetime through reference paths and growth evidence. Verify cleanup/bounds under the same workload; do not accept the explanation just because the map is static.
What is a concise interview answer for memory-leak debugging?
I first classify heap versus other memory and confirm growth under comparable load. I identify the retained owner with heap/reference evidence or native evidence, validate its lifecycle in the code, and repeat the workload to verify bounded memory and correct behavior.
