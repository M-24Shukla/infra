Use your résumé as the bridge between concepts and experience. These claims come from the résumé and your notes; they are not independently verified production measurements.

Throughput: 360K → 1.5M messages/second

Your résumé describes leading a Kafka messaging architecture revamp. Prepare the actual before/after flow, your own contribution, the bottleneck, and the measurement conditions. The ratio is about 4.17×, or a 317% increase. Distinguish offered load, accepted messages, successfully processed messages and durable acknowledgements.

  • Bring the same message size, partition count, producer/consumer count, resources, duration, acknowledgement settings and error rate into the comparison—or explain differences.

Interview questions · try answering first
How did you know the improvement was real?
Explain the load generator, counting point, steady-state window, repetitions and error/lag checks. A producer send rate can rise while consumers fall behind; that is not equivalent to an end-to-end processing improvement.
What if they ask what you personally did?
Identify the code/design or experiment you owned, the alternatives you evaluated, and what teammates owned. Use a concrete before/after example; do not substitute a team-level metric for personal contribution.

Diagnostic suite, RCA, Java and AI workflows

Your shell suite correlates Kafka health, lag, ISR, partition distribution, throughput, Kubernetes resources and operating-system signals. Your résumé states initial diagnostics fell from about 15 minutes to 15 seconds, with roughly five engineer-hours saved weekly. Describe what the timed step actually collected; avoid calling this full incident resolution.

For Java/Spring Boot/Micronaut, prepare one request or message path from entry point to storage. For AI agents and MCP workflows, explain context gathering, bounded tasks, secret handling, review and independent verification. Interview questions · try answering first
What makes a diagnostic script reliable?
Explicit namespace/context, timeouts, bounded parallelism, timestamped output, dependency checks, partial-failure reporting, exit codes, and redacted output. A failed command must not be reported as a healthy component.
What is a strong RCA story?
Impact → timeline → competing hypotheses → discriminating evidence → root cause → mitigation → permanent fix → validation. Separate correlation from mechanism and describe how recurrence is detected.
How do you validate an AI debugging suggestion?
Confirm the referenced code path and deployed configuration, reproduce the failure, and use tests or measurements whose expected results come from the requirements. AI-written tests can repeat the same mistaken assumption as its fix.
03 / Core

Docker: images, execution and builds

Explain how a Java artifact becomes a process, and how container isolation differs from a virtual machine.

Images, layers, namespaces and cgroups

An image is a layered filesystem plus execution metadata. A container is a process environment created from it, usually with a writable layer. Linux namespaces isolate views such as processes and networking; cgroups account for and constrain resource use. Containers share the host kernel, unlike a VM with its own guest kernel.

Container writable data is not durable application storage. A volume can outlive a container; a bind mount exposes a host path. EXPOSE documents a port; -p publishes it. localhost means the current network namespace, not automatically the host.

Interview questions · try answering first
Why can a container use little heap but much more memory overall?
The process also uses metaspace, code cache, native libraries, thread stacks and direct buffers. Depending on accounting, filesystem cache also matters. Heap usage and total cgroup memory are different measurements.
Does Kubernetes need the Docker daemon?
No. The kubelet talks to a CRI-compatible runtime such as containerd or CRI-O. OCI images built by Docker can run there. Docker tooling and Kubernetes runtime integration are separate concepts.

Interview questions · try answering first
Why avoid a shell-form Java startup command?
An intermediate shell may interfere with signal forwarding. Use exec form or an entry script ending with exec java ... so the JVM receives termination signals and can shut down cleanly.
Why not copy credentials and delete them in a later layer?
Earlier image layers may retain them. Use build secret mounts for build-time credentials and an appropriate runtime secret mechanism. Do not print credentials in build logs.
Is a smaller image always better?
It reduces transfer/storage and often attack surface, but must still support the application and operational plan. Distroless/minimal images may need external debug tooling rather than an installed shell.
04 / Core

Kubernetes architecture and reconciliation

Know which component acts at each stage; avoid treating Kubernetes as one process.

From Deployment YAML to running containers

The API server authenticates, authorises and admits requests. Controllers reconcile desired and observed state. A Deployment manages ReplicaSets; a ReplicaSet maintains Pods. The scheduler selects nodes for unscheduled Pods. A node’s kubelet coordinates containers through the runtime and reports status. Networking and storage plugins provide their respective integrations.

etcd stores Kubernetes API state. It is a consensus-backed key-value store, not your application volume. Its quorum is a majority: a three-member cluster tolerates one member failure. Loss of control-plane availability can prevent changes while existing workloads may keep running; that does not guarantee every workload remains healthy.

Interview questions · try answering first
Who actually starts a container: the scheduler or kubelet?
The scheduler selects a node. The kubelet on that node works with the container runtime to start and manage the container.
Why does a deleted Pod reappear?
Its controller still observes a desired replica count. It creates a replacement with a new identity/IP. Deleting a Pod is not equivalent to changing the desired Deployment.
Is etcd where my PVC data lives?
No. Kubernetes stores resource metadata in etcd. PVC contents live in the backing storage system, such as Ceph. Disaster recovery must cover both independently.

Why is my Pod Pending although node CPU usage is low?
Scheduling considers resource requests and other constraints, not only current utilisation. Check events for insufficient requested resources, affinity/taints, unbound volumes or topology restrictions.
Would three replicas guarantee high availability?
No. They can share a node or failure domain, fail the same dependency, or all be unready. Placement, capacity, dependency resilience and rollout settings also matter.

05 / Core

Health probes, rollout and graceful shutdown

A running process, a healthy process and a process ready to serve traffic are different states.

Startup vs readiness vs liveness

Startup allows initialisation to complete before other probes run. Readiness determines whether a Pod is eligible for normal Service traffic. Liveness can restart a stuck container after its failure threshold. A readiness failure alone does not restart it. Probe period, timeout and thresholds determine reaction time.

Avoid making liveness depend on every downstream service: a database outage can otherwise cause mass restarts without fixing the outage. Readiness dependencies need judgment too: removing every replica during a shared failure can eliminate useful degraded behavior. For Spring Boot, verify Actuator health group paths and exposure rather than assuming a default endpoint is enabled.

Inspect
kubectl describe pod <pod> -n <ns>
kubectl get pod <pod> -n <ns> -o yaml
kubectl get endpointslices -n <ns> -l kubernetes.io/service-name=<service>
kubectl logs <pod> -n <ns> -c <container> --previous

Interview questions · try answering first
Pod is Running but receives no requests. Why?
Inspect readiness, Service selectors, EndpointSlice readiness and port mapping. Running describes execution state; it does not prove readiness or reachability.
A Java service takes 90 seconds to start and repeatedly restarts. What do you check?
Check termination reason and probe events. If liveness is killing legitimate startup, use a startup probe with an evidence-based budget. Also rule out OOM or application exceptions instead of merely extending thresholds.

Rollout, traffic draining and termination

A rolling Deployment controls replacement using maxSurge and maxUnavailable. Extra replicas need spare resources. On termination, route removal and process shutdown are asynchronous: design for in-flight traffic. A preStop hook consumes the same termination grace budget; the process then needs time to finish or checkpoint work before forced termination.

For Kafka consumers, stop accepting new work, handle outstanding processing/offset semantics and close cleanly. For HTTP, configure framework graceful shutdown and ensure load-balancer/ingress behavior matches the drain window. A rollback can restore an image/configuration, but does not automatically reverse a database migration.

kubectl rollout history deployment/<app> -n <ns>
kubectl get deployment <app> -n <ns> -o yaml
# Changes: use deliberately
kubectl rollout undo deployment/<app> -n <ns>
kubectl scale deployment/<app> -n <ns> --replicas=3
Read in context: Deployments ↗Pod termination ↗
Interview questions · try answering first
Why can a rolling update cause 502s despite multiple replicas?
Check readiness accuracy, draining of terminating Pods, ingress upstream state, startup timing and capacity. Multiple replicas do not remove races around connections and termination.
Does a longer preStop sleep guarantee graceful shutdown?
No. It delays termination and consumes grace time. Application shutdown, routing propagation and connection behavior still need verification under a rollout test.
06 / Core

CPU, memory, JVM and autoscaling

Resource tuning must connect a limit or metric to a specific bottleneck.

Requests, limits and Java memory

Requests influence scheduling and relative resource allocation; limits constrain usage. CPU can be throttled at its limit without a restart. Memory pressure can cause termination; OOMKilled is stronger evidence than exit code 137 alone, which only indicates SIGKILL. Node pressure eviction is a different mechanism.

JVM container memory includes heap + metaspace + code cache + stacks + direct/native allocations. Leave measured headroom rather than setting Xmx equal to the memory limit. A memory-backed emptyDir also consumes memory. In a load test, correlate request rate, p99 latency, throttling, allocation/GC and total working set.

Inspect
kubectl top pods -n <ns> --containers
kubectl top nodes
kubectl describe pod <pod> -n <ns>
kubectl get pod <pod> -n <ns> -o jsonpath='{.status.containerStatuses}'
# Inside the JVM container if JDK tools and permissions are available:
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info
jcmd <pid> Thread.print
# Recording: writes a file and has diagnostic overhead
jcmd <pid> JFR.start name=incident settings=profile duration=60s filename=/tmp/incident.jfr
Read in context: Resource management ↗jcmd reference ↗
Interview questions · try answering first
Why is adding heap not the default OOM fix?
First determine whether the issue is heap retention, allocation pressure, native memory, thread growth or an undersized container. Increasing heap inside a fixed limit can reduce native headroom.
Why does low average CPU not rule out CPU trouble?
Averages can hide a saturated core, bursts or quota throttling. Examine per-container/per-core behavior and time-aligned throttling signals.
What are the limits of kubectl top?
It requires the metrics pipeline and shows recent usage, not a complete history, heap breakdown or CPU profile. Use it to orient, not prove a root cause.

HPA, capacity and dependency limits

HPA changes replica count based on configured metrics. CPU utilisation targets commonly use CPU requests as the denominator. Missing/misleading requests undermine interpretation. A metrics adapter is needed for many custom/external metrics. Stabilisation and startup effects matter.

Scaling consumers is limited by partition assignment and downstream capacity. Ten replicas with 30 database connections each can demand 300 connections. Fix the constrained resource rather than moving the queue elsewhere.

Inspect
kubectl get hpa -n <ns>
kubectl describe hpa <name> -n <ns>
kubectl get resourcequota,limitrange -n <ns>
Read in context: Horizontal Pod Autoscaler ↗
Interview questions · try answering first
If Kafka lag grows, should we always add consumers?
Check partition count, assignment skew, per-partition ordering, processing cost, broker/storage and downstream limits. Replicas beyond available partition parallelism may be idle.
Why can scaling make an incident worse?
It may multiply DB connections, retries, cache misses and pressure on a saturated dependency. Include dependency capacity and overload controls in the scaling plan.

Interview questions · try answering first
Service has no usable endpoints. What do you check?
Selector/label agreement, readiness, target Pods and EndpointSlice conditions. Then confirm that the application listens on the intended interface and targetPort.
Pod IP works but Service DNS fails. What next?
Separate name resolution from forwarding: resolve the FQDN, inspect resolv.conf/CoreDNS and DNS egress, then test the Service IP. A DNS success does not prove the Service routes traffic.

NetworkPolicy, TLS and failure classification

A NetworkPolicy selects Pods and describes allowed ingress/egress at network level. Enforcement requires supporting networking. Policies are additive; traffic may need both source egress and destination ingress permission. Explicit default-deny needs required exceptions, including DNS to the actual cluster DNS path. Standard NetworkPolicy does not express HTTP paths or general FQDN rules.

Interview questions · try answering first
Why does port-forward work while the real request fails?
It uses a different path through the API/kubelet forwarding machinery. It can bypass the ingress, load balancer or normal Service data path involved in the incident.
Does NetworkPolicy encrypt traffic?
No. It controls allowed network communication when enforced. TLS/mTLS and certificate management address encryption and peer authentication.
Would you use curl -k to fix TLS?
No. It bypasses certificate verification and can hide the fault. Inspect chain, hostname, trust and expiry; use verification bypass only as a clearly bounded diagnostic comparison if permitted.

Linux network diagnostics: packet loss, MTU, sockets and conntrack

Check the network namespace and interface that carries the flow. Compare deltas over the incident window. Retransmissions may indicate loss or reordering but do not identify the failing hop. Small requests succeeding while large requests stall suggests an MTU/PMTUD hypothesis, not proof. Connection churn can exhaust ephemeral ports or conntrack capacity.

These are Linux host/network-namespace tools. Some require privileges and installed packages. Packet capture can contain sensitive data; use a narrow filter and bounded capture. A distroless application container is not expected to contain every utility.

Interview questions · try answering first
How would you investigate an MTU mismatch?
Compare interface/tunnel MTUs and packet-size-dependent behavior from the failing namespace. Use tracepath or controlled non-fragmenting probes where permitted and inspect ICMP/packet evidence. Fix the network path rather than blindly shrinking every MTU.
What does a growing socket Send-Q suggest?
For an established TCP connection it indicates queued/unacknowledged data. Check receiver progress, advertised window, retransmissions and RTT. Queue interpretation differs for listening sockets, so first inspect socket state.

Security context, identities and access

Explain the layer each security mechanism controls: API permissions, process privileges, network reachability, storage permissions, or application identity.

SecurityContext fields and practical failure modes

Field / conceptPurpose and nuance
runAsUser / runAsGroupNumeric process UID/GID. The image and mounted files must support that identity.
runAsNonRootRequires non-root execution; it does not repair file permissions.
fsGroupSupplemental group/volume access behavior; ownership handling depends on volume and CSI driver.
fsGroupChangePolicyCan reduce recursive ownership work; driver-managed group handling may change applicability.
allowPrivilegeEscalation: falsePrevents acquiring additional privileges via mechanisms such as setuid.
capabilities.drop: [ALL]Drops Linux capabilities; add only a justified minimum.

Interview questions · try answering first
A non-root Java Pod gets Permission denied on a PVC. What do you inspect?
Inspect the effective UID/groups, mount options, file owner/mode, fsGroup and driver support. Also check SELinux/AppArmor denials and whether it is a read-only mount. Do not immediately switch to root or chmod 777.
Why can readOnlyRootFilesystem break a previously working service?
The app or JVM may write temp files, logs, extracted libraries or caches. Identify exact write paths and mount suitably sized writable volumes. Keep application logs on stdout/stderr where appropriate.
Does fsGroup always recursively chown every CSI volume?
No. Behavior depends on volume type and driver capabilities. Some CSI drivers handle mount group themselves; fsGroupChangePolicy does not control those driver-managed operations.

RBAC, service accounts, Secrets and Pod Security Admission

A ServiceAccount is a workload API identity. Roles define namespaced permissions; ClusterRoles can define broader rules; bindings grant them to subjects. Authentication identifies you, authorisation decides what you may do. Pod Security Admission can enforce Baseline or Restricted policies, with warn/audit modes for rollout.

Secret data encoded in base64 is not thereby encrypted. Use least privilege, encryption at rest where configured, short-lived identity, careful logging and a suitable secret distribution mechanism. Avoid mounting API tokens into workloads that do not need them. RBAC is separate from Linux UID and file permissions.

Interview questions · try answering first
Does root in a container automatically mean Kubernetes cluster-admin?
No. Process privileges and Kubernetes API authorisation are separate. Root/host access can still be dangerous, particularly with privileged settings, host mounts or exposed credentials.
Why can a secure-looking manifest still be rejected?
Admission can enforce additional policy, required fields or organisational restrictions. Read the rejection and policy level/version. SecurityContext configures runtime behavior; admission decides whether the specification is allowed.
How would you check access without dumping a Secret?
Use auth can-i, metadata and resource references. Do not print Secret contents or broad environment dumps into diagnostic bundles.

Network isolation example: allow one caller to one port

This example selects app=backend in its namespace and permits ingress from Pods labelled app=frontend in that same namespace, to TCP 8080. Other ingress is denied for the selected backend unless another policy allows it. It does not restrict egress, encrypt traffic or authenticate an application user. Enforcing CNI support is required. For cross-namespace callers, use namespaceSelector and podSelector together in the same peer when both conditions should apply.

Configuration example
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-from-frontend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
Read in context: NetworkPolicy examples ↗
Interview questions · try answering first
If frontend egress is default-deny, is this enough?
No. The caller also needs an applicable egress allowance to the backend, and DNS allowance if using names. Test the real client-to-server path.
What mistake changes AND into OR in policy peers?
Putting namespaceSelector and podSelector in separate list entries makes them alternative peers. Putting both in the same entry selects matching Pods within matching namespaces.

Helm: chart design, values and release debugging

Chart → values merge → template rendering → Kubernetes admission → controllers → running application.

Chart structure, values and template keywords

Chart.yaml identifies a chart and dependencies; values.yaml provides defaults; templates/ contains manifests; _helpers.tpl holds named templates; Chart.lock captures resolved dependency versions. Chart version and application appVersion are different.

Later values files override earlier ones; explicit set values override files. --set-string preserves string interpretation. Lists are typically replaced, not item-merged. Do not assume an environment variable in the Helm client becomes a chart value.

Storage: PV, PVC, CSI and Ceph

Start with the Kubernetes storage contract, then map it to Ceph components. Ceph knowledge here is study material, not a claim that you administered it.

PersistentVolume, claim, class and access mode

A PVC requests storage; a PV represents provisioned storage; a StorageClass selects provisioning policy/driver. CSI connects Kubernetes volume operations to a storage backend. A bound PVC proves binding, not successful attachment, mounting, permissions or low-latency I/O.

ReadWriteOnce generally allows read-write mounting on one node and can still involve multiple Pods there. ReadWriteOncePod is single-Pod access for supported CSI configurations. ReadWriteMany supports multi-node writers when the backend does. Reclaim policy, topology, binding mode and expansion support matter.

Interview questions · try answering first
Why can a PVC stay Pending?
Check claim/class matching, provisioner/CSI health, capacity, topology and events. WaitForFirstConsumer may intentionally defer binding until workload placement is determined.
A Pod is stuck in ContainerCreating with a bound PVC. Why?
Inspect attach/mount events, node connectivity, CSI node plugin, volume permissions and stale attachment. Do not conclude provisioning succeeded end-to-end just because binding succeeded.
Does a PV guarantee a backup?
No. Persistence across Pod replacement is not backup or disaster recovery. Replication also does not protect against every deletion, corruption or operator mistake.

Ceph architecture: RADOS, OSD, MON, MGR and CRUSH

Ceph distributes data through RADOS. OSDs store objects and participate in replication/recovery. MONs maintain authoritative cluster maps using quorum. MGR supplies management/telemetry services. CRUSH maps data placement across configured failure domains; placement groups organise object placement and recovery.

Pools can use replication or erasure coding. Replication is simple but uses more raw capacity; erasure coding can save space with computation and workload constraints. Recovery/rebalancing consumes disk and network bandwidth and can increase client latency. A nominally replicated pool is only as resilient as its actual failure-domain placement.

Is MON the gateway for every client data read/write?
No. It provides cluster map/quorum services. Clients use placement information to communicate with the relevant OSDs; do not model all data I/O as flowing through MON.
Why can performance degrade after an OSD failure?
Client work now competes with recovery/backfill, redundancy is reduced and placement changes. Correlate health/PG state, OSD latency and network/disk saturation before changing recovery settings.
What does HEALTH_WARN mean?
It is a summary, not a root cause. Read health detail for the specific condition and assess impact. A warning can range from redundancy problems to operational advisories.

11 / Depth

Ring buffers, congestion and backpressure

These connect directly to high-throughput messaging. Application queues, TCP buffers and NIC descriptor rings are different layers.

Ring buffers: bounded storage and concurrency

A ring buffer reuses a fixed array with positions that wrap around. It can avoid per-entry node allocation and improve locality. A generic array-backed ring is not automatically thread-safe or lock-free: producer/consumer coordination, publication visibility and overflow behavior must be designed.

When full, choose an explicit policy: block, reject, drop according to a stated contract, or spill durably. Overwriting unread data is not acceptable for reliable event processing. LMAX Disruptor adds sequencing and consumer dependency coordination; a slow consumer can constrain safe producer progress. Busy-spin wait strategies can consume a core and interact badly with container CPU quotas.

Read in context: Disruptor guide ↗
Interview questions · try answering first
Is a ring buffer always faster than BlockingQueue?
No. Results depend on contention, wait strategy, batching, allocation, payload ownership and CPU availability. Benchmark the actual producer/consumer topology, including p99 latency and overload.
How can object reuse introduce a bug?
A consumer may keep a reference after its slot is reused, then observe mutated data. Define ownership/lifetime and copy or complete processing before reuse.
What is the LLD connection?
A bounded queue needs a capacity, producer/consumer contract, ordering requirements, full policy, shutdown semantics and tests for wraparound and races. Choosing an array is only one design decision.

NIC rings, socket buffers and network congestion

A NIC RX/TX ring contains descriptors for packet processing, not application events. RX exhaustion can drop packets if the host does not drain fast enough. RSS spreads flows among hardware queues; RPS/RFS/XPS are related software steering mechanisms. More queue capacity may absorb bursts but can also increase waiting time; it does not create processing capacity.

TCP receiver flow control protects the receiver via its advertised window. Congestion control adapts sending to the network path. Socket buffers hold data at endpoints. A larger socket buffer does not repair packet loss, a slow application or an overloaded link. Bufferbloat means excessive queueing that inflates latency.

Interview questions · try answering first
Would you increase RX ring size to fix packet drops?
Only after confirming the drop location/counters and host processing bottleneck. Compare bursts, softirq/CPU distribution, queue balance and application throughput. Test a bounded change with latency and drop measurements.
Can ring buffers solve sustained overload?
No. If arrival rate stays above service rate, any finite buffer eventually fills. Buffers absorb bursts; capacity increases, admission control or upstream rate reduction address persistent overload.

Backpressure: keep a fast producer from overwhelming a slow consumer

Backpressure communicates or enforces downstream capacity. Examples include bounded queues that block/reject, demand signalling, consumer pause/resume and admission limits. Rate limiting caps admission according to a policy; load shedding rejects excess work. They can complement backpressure but are not interchangeable.

Example: arrival rate 12K/s, service rate 10K/s. Backlog grows by 2K/s. A queue of 20K items buys roughly 10 seconds from empty under those constant rates. A bigger queue delays failure and adds memory/latency; it does not fix the imbalance. In a stable system, Little’s Law relates average in-flight work L = throughput λ × average time W; use consistent units and scope.

Interview questions · try answering first
How do you apply this to a Java executor?
Use a bounded work queue, a deliberate rejection policy and observable queue delay/depth. CallerRunsPolicy can slow callers but may block a request/event-loop thread, so choose it with the threading model in mind.
What are the signals of overload?
Rising queue age/depth or consumer lag, increased tail latency, timeouts and rejection rates. CPU may be low if work is blocked on I/O. Find the stage that cannot sustain arrival rate.
What does Reactive Streams request(n) mean?
The subscriber signals demand for up to n additional elements. That coordinates flow within the participating chain; it does not magically make a database or arbitrary external producer backpressure-aware.

Kafka performance, reliability and overload

Connect application, broker, disk and network evidence. Healthy Pods do not prove a healthy Kafka cluster, or the reverse.

Partitions, consumer lag, ISR and producer limits

A partition is an ordering/parallelism unit. Lag is the distance between a consumer position/committed offset metric and the log end according to the tool: specify the definition. Growing lag can reflect slow processing, skew, rebalance, downstream delay or broker trouble. ISR describes replicas sufficiently caught up under broker rules; it is not a consumer health metric.

For producers, batch.size, linger.ms and compression trade batching efficiency against delay/CPU. buffer.memory and max.block.ms bound buffering/waiting behavior; they do not turn sustained overload into capacity. Acknowledgement, idempotence and broker in-sync requirements affect durability; check version-specific interactions rather than memorising defaults.

Interview questions · try answering first
How would you investigate uneven consumer lag?
Compare lag and processing rate per partition, assignments, key skew and downstream work. A hot partition cannot be fixed merely by adding idle consumers; changing partition/key design also affects ordering.
Does acks=all guarantee zero message loss in every failure?
No. It depends on ISR/minimum in-sync settings, failure patterns and producer behavior, among other configuration. Explain the exact durability contract instead of using an absolute claim.
How do you pause processing without breaking consumer ownership?
Follow the consumer/client threading contract, continue required polling/coordination, bound outstanding work and commit only according to successful processing semantics. Pause/resume alone does not make offset handling correct.

Observability, Linux and incident method

Metrics, logs, traces and operating-system signals

Metrics reveal rates, saturation and trends; logs capture discrete events; traces connect timing across calls. Use request/error/duration signals for services and utilisation/saturation/errors for resources. Compare p50/p95/p99 with sample volume; a mean hides tails. What should a 15-second diagnostic bundle contain?
Time window/context; selected Pod status/restarts/events; Kafka lag/ISR/partition signals; node CPU/memory/network/storage snapshots; command errors; a concise summary with links to raw evidence. State sampling limits.
Why can a diagnostic bundle miss the cause?

Limit parallelism, timeouts, output volume and expensive API queries; avoid polling loops with no backoff. Keep mutation separate from collection and redact sensitive data.

Interview questions · try answering first
CrashLoopBackOff after a release: what is your path?
Read container lastState/termination reason and events, then previous logs. Separate application startup failure, bad config, permissions, OOM and liveness kills. Compare deployed image/config to the previous release; verify a targeted fix with a controlled rollout.
Pods are healthy, API is slow and CPU is low. Next?
Look at request traces, connection pool wait, blocked threads, downstream latency, disk/network and CPU throttling. Low average CPU does not establish spare capacity or eliminate contention.
Service times out but Pod-local curl works. Next?

Ceph-backed Kafka throughput drops during recovery. Next?

Only the new Helm release fails. Next?

Distinguish increasing retained heap from allocation bursts, bounded/unbounded queues, thread/direct memory and cache growth. Use container history plus JVM evidence, then test memory behavior under sustained load and overload.
